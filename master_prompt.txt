### Network throughput calculation

Do not use cumulative byte counters directly as bandwidth.

Calculate throughput using successive measurements:

Upload Mbps = (Current bytes sent - Previous bytes sent) × 8 / Elapsed seconds / 1,000,000

Download Mbps = (Current bytes received - Previous bytes received) × 8 / Elapsed seconds / 1,000,000

Handle:
- Counter resets.
- Interface changes.
- Missing samples.
- Zero or invalid time intervals.
- Negative counter differences.

# 20. DEMONSTRATION REQUIREMENTS

The system must support a complete demonstration lasting approximately 5–7 minutes.

The demonstration sequence:

### Stage 1 — Normal operation

Show:
- All nodes online.
- Router healthy.
- All backends healthy.
- Load balancer active.
- Normal network traffic.

### Stage 2 — CPU spike

Trigger CPU stress on Node 1.

Show:
- CPU rising.
- Actual telemetry.
- Threshold crossing.
- Alert generation.
- Recovery after stopping the workload.

### Stage 3 — Network spike

Generate controlled network traffic.

Show:
- Upload/download throughput increasing.
- Packet counters changing.
- Bandwidth graph spike.
- Network event.
- Recovery.

### Stage 4 — Load balancing

Generate multiple HTTP requests.

Show:
- Round Robin.
- Least Connections.
- Weighted Round Robin.
- Backend request counts.
- Actual traffic distribution.

### Stage 5 — Backend failure

Stop Backend 2.

Show:
- Health-check failure.
- Backend marked unhealthy.
- Traffic redistributed.
- No new requests routed to Backend 2.
- Backend recovery after restart.

### Stage 6 — Router failure

Disable a router interface.

Show:
- Interface state change.
- Connectivity degradation.
- Packet loss.
- Alert.
- Restoration of connectivity.

### Stage 7 — SDN mitigation

Trigger a controlled test flow.

Show:
- Detection.
- Mitigation request.
- OpenFlow rule installation.
- Flow table verification.
- Traffic effect.
- Rule removal.

### Stage 8 — Final recovery

Restore normal conditions.

Show:
- All components healthy.
- No active simulations.
- Metrics returning to baseline.
- Complete event history.

All stages must operate on the actual network environment.

# 22. DEVELOPMENT RULES — STRICT

Follow these instructions throughout implementation.

### Rule 1: Inspect before modifying

Always read the existing file and understand its dependencies before changing it.

### Rule 2: Preserve functionality

Do not remove existing APIs, agent functionality or SDN capabilities without a justified migration.

### Rule 3: Work incrementally

Implement one module at a time.

### Rule 4: Test immediately

After each significant change, run the relevant tests.

### Rule 5: No fabricated results

Never create fake metrics or pretend a network operation succeeded.

### Rule 6: Maintain documentation

Update PROJECT_STATE.md after every completed milestone.

### Rule 7: Keep the architecture modular

Avoid monolithic files, duplicate implementations and unnecessary coupling.

### Rule 8: Avoid unnecessary dependencies

Use the existing stack unless a dependency provides clear technical value.

### Rule 9: Report failures honestly

If a test fails, document the failure and investigate it.

Do not hide errors or bypass verification.

### Rule 10: Do not overengineer

Build the strongest implementation within the defined demonstration scope.

Do not introduce enterprise infrastructure that is not needed to demonstrate the project's capabilities.

### Rule 11: Preserve reproducibility

Document exact installation, startup, shutdown and testing procedures.

### Rule 12: No destructive changes without approval

Back up important configuration and database files before migration.

Do not overwrite working implementations blindly.
